# Качество Personal Cosmic Book: исходное состояние и ближайший план

Дата: 2026-10-05. Основа: main f37e47e, статическое чтение кода и офлайн-проверки.
Подтверждённый приоритет владельца: «Сначала улучшить качество книги».

## Что уже есть

Книга из десяти разделов, четыре темы оформления, двухэтапная генерация
паттернов и текста через DeepSeek, детерминированный fallback. Разделение
смысла и оформления заложено в коде. Есть спецификации качества и план
оценки: `prompts/quality-validation-v4.md`, `prompts/evaluation-plan.md`.
Это наличие реализации и требований; качество живых LLM-книг ещё не измерено.

## Главные разрывы между требованиями и исполнением

1. **Неизвестное время рождения не фильтрует факты для текста.**
   `api/book.py::_chart_facts` передаёт Ascendant, если он есть и
   `astrology_available=true`, без проверки времени. `build_book` проверяет время
   только для visual assignment. Офлайн-кейс unknown-time в
   `.ai/project/quality-baseline.json` воспроизводит наличие Ascendant в фактах.
   Условие: вход содержит Ascendant при неизвестном времени; фактическую частоту
   такого входа в проде мы не измеряли.
2. **Редакторские ограничения преимущественно в промпте.**
   `_generate_sections` проверяет наличие разделов и непустых blocks, но не
   длину, доказательность утверждений, повтор тезисов и биографические выдумки.
   `_deepseek_chat` не проверяет finish_reason. Описанные в спецификациях
   evidence_refs / claim ledger / blueprint / semantic QA не проведены в этот
   двухэтапный runtime. Наличие документов не означает работу этих механизмов.
3. **Оценки на наборе профилей пока нет.**
   В `prompts/evaluation-plan.md` задано минимум 20 обезличенных профилей и
   слепая оценка двумя людьми. В просмотренных тестах такого сравнения нет.
   Для разных модельных конфигураций из документа доступность не проверялась;
   начинать следует с фактически настроенной модели, не со смены провайдера.
4. **Fallback должен быть честно показан читателю.**
   API различает `generated_with=template` и `deepseek-2stage`.
   Нужно проверить пользовательское объяснение режима и достаточность текста:
   без модельной генерации нельзя обещать ту же глубину персонализации.

## Что проверено

- `tests/test_book.py` + `tests/test_store.py`: 18 passed (0.11 s),
  Python окружение AI Ops Kit; API-ключи генерации и БД отключены для процесса.
- Четыре синтетических офлайн-кейса: известное время, неизвестное время,
  недоступная астрология, другой профиль. В каждом ровно десять разделов,
  режим template; результаты и тексты сохранены в quality-baseline.json.
- Живые вызовы DeepSeek, сравнение персонализации LLM и редакторская оценка
  НЕ выполнялись; стоимость и качество живой генерации неизвестны.
- CI перед слиянием Kit был зелёным, но это не метрика литературного качества.

## Предлагаемый порядок

1. Собрать версионированный golden set минимум из 20 синтетических/обезличенных
   профилей по существующему evaluation plan. Зафиксировать критерии:
   десять корректных разделов; запрещённые факты при неизвестном времени
   не используются; нет выдуманной биографии; повтор тезисов измеряется;
   человеческая оценка и стоимость сообщаются отдельно.
2. Закрыть фильтрацию ненадёжных фактов и добавить регрессионные проверки.
3. Провести контрактные проверки и редакторский QA в реальный runtime.
   Разделить ошибки схемы, обрезанный ответ и неприемлемый текст; проверить,
   как эти случаи превращаются в fallback и как это объясняется читателю.
4. На том же наборе сравнить текущую и улучшенную генерацию вслепую.
   4.2/5 из evaluation plan — кандидат на порог приёмки, не уже достигнутый
   результат и не подтверждённая владельцем метрика.

## За пределами ближайшей работы

Оплата и доставка: checkout создаёт платёж, но в server.py нет маршрута
подтверждения платежа; book endpoint не привязан к оплаченному заказу;
почтовая доставка не найдена, хотя UI её обещает. Эти задачи не включены
в ближайшее улучшение книги; вернуться к ним перед первыми продажами.
Продакшен-окружение и аудитория требуют подтверждения владельца.
